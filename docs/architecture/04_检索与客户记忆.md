# 检索与客户记忆详细设计

客户的可验证事实和原始记录在业务库；检索系统仅保存经处理、可重建的证据。查询始终限定登录销售人员的租户，先做权限和来源版本检查，再使用关键词或向量排序。

## 三层记忆

| 层级 | 内容 | 维护方式 |
| --- | --- | --- |
| 事实层 | 已确认姓名或代称、标签、阶段、事件、需求及其来源 | 结构化表、字段加密、版本和状态；权威 |
| 记录层 | 用户转写、发生时间、音频引用、人工修订 | 加密保存；详情页按权限读取 |
| 检索层 | 脱敏摘要、精选记录片段、768 维向量、来源和版本 | 可重建；删除、撤权或修订后立即失效 |

模型的临时上下文和对话历史不是事实数据库。每个客户基准选择约 4 个对经营有用的检索片段，按时间和重要性更新；并非每次沟通永久生成多个向量。客户原始事实和历史记录仍按其实际保留期限保存。

## 入库流程

1. 记录已确认且允许相应处理后，按人物和主题切分；每片段记录 tenant_id、customer_id、record_id、record_revision、segment_id 和时间。
2. 在受控环境删除或替换姓名、证件、电话等直接标识，并最小化准标识及健康等敏感内容。脱敏文本仍可能可识别，按个人信息管理。
3. 生成 text-embedding-v4 的 768 维文档向量，同时使用经验证的中文分词建立脱敏文本关键词索引。不能将明文客户原文复制到 JSONB、tsvector、向量元数据或日志。
4. 写入 search_chunk，记录 embedding_model、dimension、normalization_version、source_revision 和 indexed_at；写前再检查记录版本和访问状态。
5. 当用户修改、删除、撤权或合并时，先标记相关块不可检索，异步更新或删除；重建期间读取权威库的来源状态，不能返回过期片段。

向量和倒排索引要有磁盘加密、租户访问控制和审计。向量字段本身不能直接用普通不可搜索的字段密文完成相似度计算；若需要字段级强加密检索，须另行评估受保护执行环境或同态计算的实际代价和能力。

## 查询管道

1. API 从登录态取租户及权限；在受控服务中对用户输入进行敏感内容检测。查询里指定的客户姓名先通过租户内安全令牌或人工选择解析成 customer_id；同名询问用户。
2. 结构化条件（如阶段、时间、任务状态）走 SQL 过滤。姓名或联系方式等精确匹配使用租户 HMAC；部分匹配只在受限候选集中解密比较，不通过普通哈希或全局索引实现。
3. 对不含直接标识的语义问题生成查询向量，并并行召回脱敏关键词结果。先由租户和权限缩小集合，再精确计算向量距离，使用 Reciprocal Rank Fusion 等方式融合，来源去重后保留有限证据。
4. 对候选逐条检查所属租户、客户状态、记录版本、授权与删除墓碑；过滤过期或无权限的证据。最终仅发送必要片段及来源占位编号给模型。
5. 输出时服务端核验每个来源编号，展示可点击的授权记录。若没有足够的相关证据则明确“资料不足”；不能单凭向量近似度判断保险需求或身份。

一个可评测的初始配置为：每条查询取关键词前 20 条、向量前 20 条，融合去重后最多 8 个片段，总上下文不超过 2000 token；数值经样本评测调整。禁止把未经校准的相似度阈值作为准确概率。

## pgvector 的租户过滤

每名销售人员通常只有数百到一千客户，优先使用 tenant_id 的 B-tree 将其片段取出，在受限集合内进行精确距离计算。以下是查询形态示例，具体索引和执行计划须以真实数据压测：

```sql
WITH tenant_chunks AS MATERIALIZED (
  SELECT s.chunk_id, s.source_ref, s.embedding
  FROM search_chunk s
  JOIN record r ON r.tenant_id = s.tenant_id AND r.record_id = s.record_id
  JOIN customer c ON c.tenant_id = s.tenant_id AND c.customer_id = s.customer_id
  WHERE s.tenant_id = :verified_tenant_id
    AND s.customer_id = :authorized_customer_id
    AND s.state = 'active'
    AND s.source_revision = r.revision
    AND r.storage_state = 'stored' AND r.deleted_at IS NULL
    AND c.deleted_at IS NULL
    AND EXISTS (
      SELECT 1 FROM record_person_link l
      WHERE l.tenant_id = s.tenant_id AND l.record_id = s.record_id
        AND l.revision = s.source_revision AND l.customer_id = s.customer_id
        AND l.status = 'confirmed'
    )
)
SELECT chunk_id, source_ref
FROM tenant_chunks
ORDER BY embedding <=> :query_vector
LIMIT 20;
```

该示例适用于记录片段且业务库与索引同库；每条片段连接其自己的来源版本，不用单一 revision 过滤所有记录。聚合摘要需另行校验全部 suggestion_evidence 或等效来源表。独立检索库不能使用此跨库 JOIN，须取候选 ID 后向权威业务服务批量校验，并在发给模型前和交付答案前再次检查 policy_epoch；权威服务不可达时拒绝返回受保护内容。

全局近似 HNSW 索引先扫描后按租户过滤时可能返回不足的候选；若未来改用 ANN，必须评估实际过滤召回、迭代扫描、分片及租户隔离，而不是只比较延迟。[pgvector 过滤说明](https://github.com/pgvector/pgvector)。至少评测 Recall@K、证据命中率、误引用率及 P95/P99，检索服务端 P95 目标为 500 毫秒，需使用真实规模和并发验证。

## 版本切换

更换 embedding 模型、维度、中文分词或脱敏规则时，不覆盖旧索引直接混算。新版本建立独立索引，按 tenant_id 回填，期间新写入双写；抽样比对召回和来源权限后灰度切换，保留回滚窗口，再删除旧版本及已失效数据。回填和查询 embedding 会消耗额外 token、存储和服务配额，预算单列。

## 评测

建立经授权或合成的客户问题集，覆盖同名、相似家庭情况、长时间未联系、转写错字、否定表达、用户更正、缺少证据与删除后查询。对每例记录标准客户、证据和期望拒答；同一问题测试租户隔离。分开统计检索召回、答案事实正确性、引用有效性和无依据回答，不以采纳率代替准确率。

## 检索完整性与删改竞态

每客户四个片段只是热索引预算假设，不是历史事实删除策略。对明确的旧时间、主题或保单服务查询，优先查询结构化索引和脱敏的历史关键词，再按需加载授权片段；若历史未索引，标注检索覆盖范围并允许用户打开原始时间线，不能将“热索引未找到”回答成“从未发生”。冷查询加上超时、分页和租户预算。

中文关键词初期在应用内用经授权词典的中文分词器形成词项，以 PostgreSQL simple 配置维护 tsvector；停用词和保险术语词典版本化，不能将客户姓名加入公共词典。发布前评测中文、混合英文、错字及否定句，按真实托管环境检验执行计划。

缓存键包含 tenant_id、权限 epoch、客户/来源版本、模型版本与查询摘要；缓存仍须当前权限校验。生成途中来源被删或撤权，最终答复须撤回而不是继续流式暴露；MVP 采用检查通过后整段展示，只有安全设计成熟后再启用逐 token 展示。已交付给用户或供应商的旧信息不能被技术性“收回”，隐私流程应诚实说明。
