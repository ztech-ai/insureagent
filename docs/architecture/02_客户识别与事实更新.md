# 客户识别与事实更新设计

本模块只在单个销售人员的数据空间内识别客户。系统的目标是主动提示并辅助归档，同时控制错误合并风险；不能根据模型的一句判断就改变已有客户身份。

## 对象和原则

- 客户档案创建时生成 UUIDv4；一个销售人员可以对同一自然人有重复待合并档案，但不同销售人员之间不自动匹配或共享。
- 一次记录是一份来源，可按人物和片段关联多个客户。事实、关系及任务均引用来源及记录版本。
- 用户手工确认的信息优先于机器抽取；模型的推测不作为客户已表达的事实。
- 档案合并与记录关联是两个操作。首期档案合并必须由用户明确确认，保留可撤销映射。

## 解析步骤

1. 接收已保存记录的版本、发生时间、用户预选客户及转写；预选只表示本次关联上下文，不证明所有提到的人都是该客户。
2. 在受控环境中进行姓名、称谓、电话及证件等识别，构建任务内人物占位符；对匹配所需标识进行规范化和租户专属 HMAC，直接标识符不进入模型。
3. 先根据精确令牌、用户选择的客户和确认过的别名在本租户召回；再在受限候选集中结合称谓、历史上下文和用户可见的辅助信息做排序。匹配仅用于候选，电话号码可能被多人共用，姓名可能重名。
4. 口述只提一个明确预选客户、且无冲突时，可自动关联记录。其他身份识别默认走待确认；将来仅在唯一标识加独立证据、无冲突、并通过严格误关联评测时灰度允许自动关联。模型自评分不能替代规则和人工评测。
5. 不足以建立身份时保留未归档记录；用户可选择现有客户、新建、拆分片段或暂缓。用户确认前不把候选事实写为已确认客户事实。

候选结果包含客户 ID、用户允许看到的脱敏名称、可解释证据类型、最近联系时间、是否冲突和当前版本；不显示其他租户或完整敏感标识。客户候选的排序分数是内部校准信号，不显示成未经校准的“概率”。

## 多人和身份冲突

记录先切分为包含角色、指代和来源偏移的片段；同一片段可关联多位客户，但事实的主体不明确时必须待确认。提到客户的配偶或孩子时只记录待确认的关系，不自动创建独立客户。存在同名、家庭共用电话、名称变化、语音识别低质量、用户描述自相矛盾等情况时进入待确认。

客户资料手工更名或号码变化只增加字段版本，不因老值继续命中而自动覆盖新值。号码和证件只在必要且具备处理依据时保存；仅以带密钥令牌查找不会解决共享号码和误识别问题。

## 事实模型和冲突策略

每条事实至少含：fact_id、tenant_id、customer_id、fact_type、加密值或受控引用、发生时间、record_id、record_revision、证据片段、提取版本、状态、人工确认人、版本和可选有效期。

| 状态 | 意义 | 进入条件 |
| --- | --- | --- |
| proposed | 模型候选 | 证据和主体可定位，但未得到用户确认 |
| confirmed | 用户确认或明确人工输入 | 用户明确确认选定事实，或直接手工录入；模型规则不授予此状态 |
| superseded | 被更正的新版本替代 | 人工更正或用户确认新值 |
| retracted | 来源撤回、删除或不再有处理依据 | 删除、撤权或事实纠错 |

人工作出的更正不会被旧版异步结果覆盖；模型候选与已确认事实冲突时产生待确认差异，不直接修改前值。历史事实不等同当前事实，如家庭情况或投保需求变化需保存发生时间及有效期。收入、疾病、投保资格等不得仅由模型推测写入。

## 操作及并发

POST /v1/records/{id}/resolution 请求携带记录版本、片段到客户的绑定、是否新建以及 Idempotency-Key。服务端锁定该租户记录，验证版本、客户归属、套餐与记录状态，在同一事务中写入绑定、事实候选和 outbox。重复同键同体返回原结果；同键异体返回冲突。

客户合并先展示冲突预览。确认时锁定两档案并验证版本，将被合并档案标记为重定向，保留双方原始事实、来源和 before/after 操作记录；不物理覆盖来源。撤销时重建原关联并处理合并后新增或已修改的记录：能无歧义恢复的自动恢复，存在冲突的进入人工核对，不承诺覆盖所有后续人工编辑。

用户修改转写时创建新 revision，旧 revision 及从中提取的事实被标记过期；检索索引和建议立即不可见，异步事件再重建。并发的旧模型任务提交时校验 record_revision 和删除状态，过期则丢弃。删除以墓碑约束所有引用和后续重放。

## 指标与验收

- 自动关联前进行人工标注测试，分别统计准确率、召回、自动关联覆盖率与漏召回；目标自动关联准确率单侧 95% 置信下限至少 99.9%。独立且有代表性的 3000 条零错误样本约可达到该下限，样本不足时保留人工确认。
- 按同名、共享电话、口音、错字、多客户、亲属、号码变更、缺少姓名和跨租户访问分别出具结果；整体平均值不能掩盖子类别失效。
- 回放同一请求及消息不重复建档、不产生重复事实；记录编辑、合并撤销及删除后的旧任务不能污染结果。
- 监控待确认积压、确认耗时、用户改选比例、用户撤销率和误关联事件；持续复核样本，而非把模型分数当业务准确率。

## 客户经营状态与事实确认

新增 contact_policy：allowed_channels、quiet_hours、do_not_contact、paused_until、reason、policy_epoch、updated_by、updated_at。首次未知渠道不自动视为已获营销同意；勿扰标记立即阻断自动经营，恢复需要用户明确操作并检查合法依据。勿扰不是删除，也不是撤回个人信息处理依据，界面分别提供入口。

一个客户可有多个 opportunity，每条保存主题、用户确认的需求或待验证假设、来源、stage、next_action、owner、version、closed_reason。初始阶段为待了解、需求已确认、方案沟通、考虑中、已结束；结束结果由用户记录。首期可手动管理需求标签和任务，后续版本再上线完整机会看板。

支持“只归档记录”和“归档并确认所选信息”。批量确认必须向用户呈现具体字段和值，不能通过一个含糊的“保存”把所有推测转为已确认。单项纠错保留旧来源，冲突不静默覆盖。错误合并撤销后，对合并后产生的新事实和任务逐项核对。
